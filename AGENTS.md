# Агент: Neuro ROP Assistant

CLI + FastAPI + React для анализа лидов/сделок Bitrix24; CRM только на чтение.

## Контекст и карта

- `api/` — HTTP/jobs; `bitrix/` — CRM; `openai_api/` — audio/анализ/change detection; `storage/` — SQLite; `frontend/` — UI; `tests/` — проверки.
- Начни с `git status --short`. Чужие изменения не трогай.
- Загружай: этот файл → [карта](ARCHITECTURE.md) (Source of Truth, Critical Invariants, нужная строка Where to change code) → релевантный документ → указанные исходники, callers и тесты. Читай только нужное.
- Код и конфигурация — источники истины; расхождения документации исправляй по фактам. [Рабочий порядок](Docs/agent_workflow.md) содержит маршруты документов, handoff и проверки.

## Критические ограничения

- Никаких write-методов Bitrix. Bitrix/OpenAI/production запускай только по необходимости задачи; платные действия и деплой требуют явного разрешения.
- Не печатай/коммить секреты, webhook URL, CRM-данные, аудио, транскрипты, содержимое `reports/` и приватные логи.
- Текст — UTF-8, кириллица без транслита/Unicode-escape; JSON — `ensure_ascii=False`. Бизнес-время — `Europe/Moscow`.
- Не обходи change detection без явно запрошенного `--allow-direct-llm`; Markdown анализа — только после validation JSON. Knowledge/OKF не являются фактами клиента.
- Lead/deal-контракты раздельны. Попытка связи, подтверждённый контакт и внутренняя CRM-информация — разные факты. Авторизация — только серверная сессия.

## Orchestration

- Primary agent — текущий агент, выбранный пользователем в треде. Не создавай отдельного lead/orchestrator, Sol, Astra или второго primary. Primary понимает и декомпозирует задачу, держит архитектуру и контракты, выбирает делегирование, интегрирует результаты и выполняет финальную приёмку.
- В Codex implementation subagents — только Luna workers; в Cursor используй доступные встроенные subagents без фиксирования модели. По умолчанию отдавай workers выгодные bounded implementation, широкое исследование и тяжёлые проверки; малое известное изменение, интеграционную правку и критическое решение primary может выполнить сам, включая чтение и написание кода.
- При выборе workers прочитай [model routing и лимиты](Docs/agent_workflow.md#model-routing). Worker получает цель, область, ограничения, результат и проверки; один файл одновременно имеет одного writer. Обычно запускай до 2 workers, для большой задачи — до 3 только на независимых workstreams и при реальном ускорении.
- Минимальное изменение в существующем слое; HTTP/SQLite правила и handoff — в рабочем порядке. Не дублируй бизнес-логику.

## Context Efficiency

- Primary agent получает от worker короткий handoff `FINDINGS / CHANGES / FILES / RISKS / VERIFICATION`, без chain-of-thought, полного transcript и огромных логов. Если следующий осмысленный шаг зависит от worker, дождись handoff и не дублируй его работу; параллельно выполняй только действительно независимую полезную задачу.
- В Codex `code_mapper` остаётся вне обычной worker quota; в Cursor используй доступный встроенный read-only scout с лимитами текущей среды. Scout не редактирует код, не принимает архитектурные или бизнес-решения и не запускает других агентов. Не запускай несколько scouts для одной области; несколько допустимы только для независимых областей при явной экономии времени или контекста.
- Используй read-only scout для широкого исследования, неизвестной части системы, большого файла, нескольких связанных файлов, поиска реализации, callers/callees, call chain и связанных тестов. Файлы примерно от 600 строк — только ориентир, не запрет на прямое чтение.
- Если файл и нужный диапазон уже известны, читай их напрямую. Известный небольшой диапазон большого файла тоже не требует subagent; полный файл можно прочитать самостоятельно, когда он действительно нужен.
- После scout самостоятельно прочитай оригинальные `RELEVANT_RANGES`, влияющие на решение. Не меняй важную бизнес-логику только по его summary.
- Особенно внимательно проверяй релевантные диапазоны сам для security/auth, concurrency и race conditions, сложных state machines, migrations/data integrity, cross-cutting business logic и архитектурных стыков между workers.
- После реализации проверь diff и выполни только релевантные tests/typecheck/lint.

## Команды и завершение

- Запуск: [README: локальный запуск агентом](README.md#локальный-запуск-агентом-для-проверки-ui) — точные команды для API/frontend, Happ и ограничений песочницы; API запускает автоматический CRM/LLM-цикл — для локального smoke отключи `DAYTIME_CYCLE_ENABLED`.
- Сначала targeted checks; после Python-логики один полный `./venv/Scripts/python.exe -m unittest discover -s tests` на интегрированном результате.
- После frontend: в `frontend/` — `npm run lint`, `npm run build`.
- Всегда `git diff --check`, проверка scope, diff и контракта. Не повторяй успешные проверки без новой причины. Укажи пропуски и причины; непроверенный результат не называй завершённым.
