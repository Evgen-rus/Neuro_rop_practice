# Экономная работа агентов

Цель — минимальная суммарная стоимость надёжно завершённой задачи, включая чтение, координацию, исправления и проверки. Читай нужный раздел; продуктовые знания остаются в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Model routing

Единственный раздел с политикой моделей разработки; модели продуктового LLM-пайплайна от неё не зависят.

| Роль | Модель / reasoning | Применение |
| --- | --- | --- |
| Lead / orchestrator | Astra (`gpt-6-astra`), `low` | Понимание, декомпозиция, выбор контекста/workers, архитектура, интеграция, конфликты, приёмка; маленькую задачу выполняет сам |
| Worker | Luna (`gpt-5.6-luna`), `low` | Scouting, usages, безопасное чтение логов, факты, документация, простые проверки/тесты и рутинные локальные правки |
| Сложный worker | Luna (`gpt-5.6-luna`), `max` | Основная нетривиальная реализация, bounded-компонент, сложный локальный debugging/рефакторинг, глубокий анализ модуля; не для тривиального |
| Эскалация текущего lead | Astra, `medium` | Сложная архитектура, несколько систем, тяжёлый debugging, важная миграция, высокий риск регрессии, противоречия workers или ненадёжная попытка на Low |

- По умолчанию один lead и до **2 workers одновременно**, из них максимум **1 Luna Max**. Для большой задачи допустимы **3 workers** только при независимых областях и явной выгоде; учитывай более строгий лимит среды. Лимит общий, включая потомков; worker не делегирует дальше без решения lead.
- Дополнительную Astra по умолчанию не создавай. Сначала повышай текущего lead до Medium; вторую Astra не запускай, если достаточно текущей Astra + Luna. High/Max у lead — только с крайне веской, кратко зафиксированной причиной.
- Маленькая задача — lead; средняя — lead + один worker; большая — 2–3 независимых workers при выгоде. В архитектурно сложной задаче workers исследуют/реализуют ограниченные части, решение остаётся у lead. Размер сам по себе не повод увеличивать число агентов.
- Это политика выбора, а не автоматическая настройка Codex. Проверяй model IDs/reasoning в текущем инструменте. Если переключение текущего lead недоступно, сообщи об ограничении; не утверждай, что модель переключена, и не создавай заменяющего lead ради обхода. Недоступную модель не подменяй молча более дорогой.

## Контекст и делегирование

1. Lead определяет scope и критерий готовности, проверяет дерево, читает карту и инварианты. Поиск — `rg --files` / `rg -n` в нужных путях; сначала имена и ссылки, затем фрагменты. При обрезанном выводе дочитай недостающий фрагмент, а не весь файл заново.
2. Перед каждым spawn кратко укажи: зачем worker, почему работа lead дороже, минимальную достаточную модель, точную область и результат. Если handoff дороже задачи — выполни сам. Большую реализацию и обзор безопасно отделимого модуля отдай подходящему worker.
3. Передай только цель, пути/символы, ограничения, результат и проверки. Используй fresh context (`fork_turns="none"`, если доступен), явно передай обязательные проектные правила и ссылки. Полная история нужна лишь при зависимости от неё. Секреты и частные данные в handoff не включай.
4. Не исследуйте одну область несколькими агентами без конкретного риска, требующего независимой проверки. Scouting может идти параллельно работе lead. Для правок назначь владельца файлов; при общей файловой системе исключи одновременную запись. Worktree используй при необходимости изоляции; отдельные пользовательские задачи создавай только по явному запросу.
5. Повторно используй worker для уточнения. Зависимые изменения выполняй после согласования контракта. Lead читает handoff и итоговый diff, проверяет стыки и спорные факты, а не перечитывает весь scout-контекст.

Короткий handoff, без chain-of-thought и пересказа прочитанного:

```text
FINDINGS: факты/решения со ссылками path:line
CHANGES: что изменено или none
FILES: затронутые файлы
RISKS: ограничения, зависимости, нерешённые вопросы или none
VERIFICATION: команда, результат, проверенная версия/diff; пропуски и причины
```

Не создавай пустые документы и дубли карт. Общие документы в `Docs/` требуют точечного исключения в `.gitignore`; клиентские материалы остаются исключёнными.
- Локальные планы в `Docs/` и README отдельных модулей не заменяют текущий код, validation и package scripts. Отсутствующие документы не восстанавливай догадками.

## Проверки и команды

Команды — из корня в PowerShell, кроме отмеченных frontend/VPS. Не устанавливай зависимости заново, если окружение готово.

| Изменение | Сначала | Перед завершением интеграции |
| --- | --- | --- |
| Документация | Пути/якоря, команды по коду, сохранность правил, UTF-8 | `git diff --check`, diff/scope; Python/frontend не нужны |
| Python-логика | `./venv/Scripts/python.exe -m unittest discover -s tests -p 'test_<область>*.py'` с реальным именем | Один `./venv/Scripts/python.exe -m unittest discover -s tests` |
| Frontend | В `frontend/`: `node --test src/<реальный-тест>.test.mjs`; для общих helpers — `npm run test:ui` | В `frontend/`: `npm run lint` и `npm run build` (включает `tsc -b`) |
| HTTP/SQLite/общий lead-deal слой | Релевантные contract/regression tests обеих сторон; второй контур проверить на несовместимость | Обязательные команды затронутых слоёв выше |
| Deploy/config | Workflow, compose, shell и `tests/test_temporary_tunnel_deploy.py` по scope | Проверки конфигурации по runbook; runtime только при разрешённом запуске |

API smoke: сначала `$env:DAYTIME_CYCLE_ENABLED='false'`, затем `./venv/Scripts/python.exe -m uvicorn api.app:app --host 127.0.0.1 --port 8000`; health — `http://127.0.0.1:8000/api/health`. Отключение scheduler не отключает ручные AI/CRM-действия: не вызывай их для smoke. Старт API может инициализировать локальную SQLite; проверка документации не требует запуска.

UI: в `frontend/` — `npm run dev`. CLI: `./venv/Scripts/python.exe run_rop_assistant.py --help` для аргументов; pipeline без аргументов не использовать как проверку документации.

Деплой на VPS (Bash): `./deploy/temporary-tunnel.sh` по runbook. Push в `main` запускает checks и автоматический deploy через `.github/workflows/deploy-main.yml`; не используй push как проверку документации.

Worker запускает targeted checks; lead — общие обязательные проверки один раз после интеграции. Успешный результат переиспользуй, если проверенные файлы/зависимости не изменились. Повтор — при новых изменениях, сбое или нерешённом риске. Не сокращай проверки корректности, безопасности и входной валидации ради бюджета. Финал: изменения, затронутый контракт, результаты проверок и явные пропуски с причинами.
