# Экономная работа агентов

Цель — минимальная суммарная стоимость надёжно завершённой задачи, включая чтение, координацию, исправления и проверки. Читай нужный раздел; продуктовые знания остаются в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Model routing

Единственный раздел с политикой моделей разработки; модели продуктового LLM-пайплайна от неё не зависят.

### Codex

| Роль | Модель / reasoning | Применение |
| --- | --- | --- |
| Luna Low worker | Luna (`gpt-5.6-luna`), `low` | Scouting, usages, безопасное чтение логов, факты, документация, простые проверки/тесты и рутинные локальные правки |
| Luna Max worker | Luna (`gpt-5.6-luna`), `max` | Основная нетривиальная реализация, bounded-компонент, сложный локальный debugging/рефакторинг, глубокий анализ модуля; не для тривиального |
| Code mapper | GPT-5.6 Luna Medium | Read-only mapping репозитория: реализации, symbols, callers/callees, call chain, связанные tests и точные source ranges; не редактирует код, не принимает архитектурные или бизнес-решения и не запускает агентов |

### Cursor

Используй доступные встроенные subagents и не фиксируй их модель: доступность зависит от текущей версии, режима и тарифа.

### Общие правила

- Primary agent — всегда текущий агент, выбранный пользователем в треде. Не закрепляй за этой ролью модель, не создавай отдельного lead/orchestrator, Sol, Astra или второго primary и не эскалируй задачу через их создание.
- В Codex единственные implementation workers/subagents — Luna Low и Luna Max; `code_mapper` остаётся отдельным read-only scout.
- По умолчанию одновременно запускай до **2 workers**. Для большой задачи допустимы **3** только при независимых workstreams, реальном ускорении и поддержке среды. В Codex не ограничивай число Luna Max искусственно; в любой среде не запускай workers ради количества и не поручай нескольким workers запись в один файл.
- Маленькую известную задачу primary выполняет сам; среднюю может отдать одному worker; большую делит между 2–3 независимыми workers при выгоде. Workers не делегируют дальше. Это политика выбора, а не автоматическая настройка Cursor/Codex; доступные model IDs/reasoning проверяй в текущем инструменте.

## Контекст и делегирование

1. Primary понимает и декомпозирует задачу, держит общую архитектуру и контракты, выбирает делегирование, получает сжатые результаты, принимает дальнейшие решения, проверяет интеграцию и выполняет финальную приёмку. Он может читать и писать код, особенно для малого изменения, известного файла/range, небольшой интеграционной правки или критического решения. Не превращай primary в слепого диспетчера, но и не делай implementation его основной ролью.
2. Отдельная просьба пользователя о worker или read-only scout не нужна. По умолчанию выгодные bounded implementation, исследование больших областей и тяжёлые проверки отдавай worker: он может искать callers/callees, писать backend, frontend и тесты, исправлять баги, локально рефакторить, запускать targeted/full tests и анализировать failures. В Codex простую отделимую работу отдавай Luna Low, нетривиальную реализацию и глубокий локальный анализ — Luna Max; широкий read-only mapping — `code_mapper`. В Cursor выбирай подходящий встроенный subagent. Если handoff дороже задачи — primary выполняет её сам.
3. Передай только цель, пути/символы, ограничения, результат и проверки. Используй fresh context (`fork_turns="none"`, если доступен), явно передай обязательные проектные правила и ссылки. Полная история нужна лишь при зависимости от неё. Секреты и частные данные в handoff не включай.
4. Параллельно запускай workers только для действительно независимых workstreams, например backend, frontend и отдельного тестового/интеграционного контура. Один файл одновременно имеет одного writer. Не исследуйте одну область несколькими агентами без конкретного риска независимой проверки; несколько read-only scouts допустимы только для независимых областей при явной выгоде.
5. Если следующий осмысленный шаг primary зависит от результата worker, дождись handoff: не дублируй работу, не перечитывай те же файлы без причины и не занимайся speculative work. Пока worker работает, primary может выполнять действительно независимую полезную задачу. Никакой отдельный runtime, scheduler или state machine для этого не нужен.
6. Primary читает handoff и итоговый diff, проверяет стыки и спорные факты. Для security/auth, migrations/data integrity, concurrency/race conditions, сложных state machines, cross-cutting business logic и архитектурных стыков между workers он лично читает нужные исходные диапазоны, а не весь репозиторий.

Короткий handoff, без chain-of-thought и пересказа прочитанного:

```text
FINDINGS: факты/решения со ссылками path:line
CHANGES: что изменено или none
FILES: затронутые файлы
RISKS: ограничения, зависимости, нерешённые вопросы или none
VERIFICATION: команда, результат, проверенная версия/diff; пропуски и причины
```

Не передавай chain-of-thought, полный transcript worker, огромные логи и тысячи строк успешных тестов. Успешный full suite сокращай до `full suite PASS — 950 tests`. При ошибках укажи итог (`948 passed, 2 failed`), список `FAILED` и только релевантный фрагмент ошибки.

## Проверки и команды

Команды — из корня в PowerShell, кроме отмеченных frontend/VPS. Не устанавливай зависимости заново, если окружение готово.

| Изменение | Сначала | Перед завершением интеграции |
| --- | --- | --- |
| Документация | Пути/якоря, команды по коду, сохранность правил, UTF-8 | `git diff --check`, diff/scope; Python/frontend не нужны |
| Python-логика | `./venv/Scripts/python.exe -m unittest discover -s tests -p 'test_<область>*.py'` с реальным именем | Один `./venv/Scripts/python.exe -m unittest discover -s tests` |
| Frontend | В `frontend/`: `node --test src/<реальный-тест>.test.mjs`; для общих helpers — `npm run test:ui` | В `frontend/`: `npm run lint` и `npm run build` (включает `tsc -b`) |
| HTTP/SQLite/общий lead-deal слой | Релевантные contract/regression tests обеих сторон; второй контур проверить на несовместимость | Обязательные команды затронутых слоёв выше |
| Deploy/config | Workflow, compose, shell и `tests/test_temporary_tunnel_deploy.py` по scope | Проверки конфигурации по runbook; runtime только при разрешённом запуске |

API smoke: сначала `$env:DAYTIME_CYCLE_ENABLED='false'`, затем `./venv/Scripts/python.exe -m uvicorn api.app:app --host 127.0.0.1 --port 8000`; health — `http://127.0.0.1:8000/api/health`. Отключение scheduler не отключает ручные AI/CRM-действия: не вызывай их для smoke. Старт API может инициализировать локальную SQLite; проверка документации не требует запуска.

UI: в `frontend/` — `npm run dev`. CLI: `./venv/Scripts/python.exe run_rop_assistant.py --help` для аргументов; pipeline без аргументов не использовать как проверку документации.

Деплой на VPS (Bash): `./deploy/deploy-production.sh` по runbook. Push в `main` запускает checks и автоматический deploy через `.github/workflows/deploy-main.yml`; не используй push как проверку документации.

Worker запускает targeted checks своей области. Общие обязательные проверки интегрированного результата primary обязан обеспечить один раз, но сам запуск тяжёлого full suite может делегировать worker. Primary получает сжатый итог и изучает подробности failures только при необходимости. Успешный результат переиспользуй, если проверенные файлы/зависимости не изменились. Повтор — при новых изменениях, сбое или нерешённом риске. Не сокращай проверки корректности, безопасности и входной валидации ради бюджета. Финал: изменения, затронутый контракт, результаты проверок и явные пропуски с причинами.
