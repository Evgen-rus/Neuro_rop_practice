# Сбор данных в течение дня и отчёт по траектории менеджеров

Эта инструкция описывает два связанных, но разных контура:

- автоматический дневной цикл API, который обновляет рабочий пул сделок, собирает CRM-факты и запускает change-aware проверку анализа;
- ручной CLI `scripts/manager_trajectory.py`, которым можно дозабрать CRM-факты или построить локальную ретроспективу за выбранную дату.

Все даты и расписание ниже — по московскому времени (`Europe/Moscow`). Bitrix используется только для чтения.

## Коротко: что запускать

Показать уже собранный локальный отчёт за выбранный день, ничего не скачивая:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report --from 2026-08-20 --to 2026-08-20
```

Дозабрать данные за сегодняшний незавершённый день до текущего момента:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py collect --from 2026-08-20
```

После успешного сбора снова построить локальный отчёт:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report --from 2026-08-20 --to 2026-08-20
```

Важно: для текущего незавершённого дня у `collect` не указывайте `--to` одной датой. Значение `--to 2026-08-20` трактуется как `2026-08-21 00:00 МСК` и может преждевременно сдвинуть watermark сбора в будущее. Для текущего дня используйте только `--from`; верхней границей автоматически станет фактическое время запуска.

## Как работает автоматический сбор

Автоматический цикл живёт внутри процесса FastAPI. Он запускается вместе с API, если `DAYTIME_CYCLE_ENABLED=true`.

В рабочие дни с 08:00 до 18:00 МСК каждые 30 минут выполняются три последовательных шага:

1. Read-only синхронизация рабочего пула deal-control: сделки, открытые задачи Bitrix и дневные коммуникации.
2. Сбор manager trajectory: CRM-активности ответственных менеджеров и наблюдаемые изменения стадий лидов и сделок.
3. Change-aware проверка активных сделок: решение `FULL`, `MINI` или `skip` принимает существующий decision engine с `force_llm=False`.

Само наступление временного слота не означает обязательный платный LLM-вызов. Однако третий шаг может скачать аудио, выполнить транскрибацию и вызвать OpenAI, если change detection выберет полный анализ. Оценка расходов записывается в `logs/daily_spend/`.

В 15:45 МСК цикл не запускает новую синхронизацию или новый анализ. Он публикует неизменяемый отчёт «Авто · к планёрке» из состояния, которое уже было сохранено к предыдущим запускам, в том числе к слоту 15:30.

Если API выключен, автоматический сбор не работает. После запуска API планировщик ждёт следующий будущий слот, а не запускает цикл немедленно.

Проверить состояние планировщика при запущенном API:

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/health).daytime_cycle | Format-List
```

Основные поля:

- `enabled` — разрешён ли цикл настройкой;
- `running` — жив ли поток планировщика внутри текущего API-процесса;
- `next_at` — следующий слот по Москве;
- `last` — безопасный агрегат последнего запуска без CRM-содержимого.

Для запуска интерфейса только на сохранённых данных отключите цикл на время текущей PowerShell-сессии:

```powershell
$env:DAYTIME_CYCLE_ENABLED = 'false'
.\venv\Scripts\python.exe -m uvicorn api.app:app --reload --host 127.0.0.1 --port 8000
```

## Что именно сохраняет manager trajectory

Сбор использует `manager_ids` из настроенного deal-control scope, если они не переопределены параметрами команды.

В SQLite сохраняются фактические append-only события:

- CRM-активности лидов и сделок, где выбранный менеджер указан ответственным;
- тип активности, provider, направление, признак завершения и все доступные времена;
- темы и описания писем, сообщений и задач, коммуникации, результаты и метаданные файлов;
- комментарии CRM-таймлайна, написанные настроенным менеджером, и зеркала Max/WhatsApp/Telegram из того же таймлайна как наблюдаемые коммуникации карточки ответственного;
- доступную историю изменений задач и историю входов в стадии;
- изменения согласованного набора значимых бизнес-полей между снимками;
- наблюдаемые presence-снимки `IS_ONLINE` и `LAST_ACTIVITY_DATE`;
- наблюдаемая смена стадии между двумя успешными срезами;
- создание рекомендаций НейроРОПа и Quick Help;
- показы и просмотры рекомендаций, только когда их выполнил серверно подтверждённый менеджер своей сделки.

Повторный сбор того же события безопасен: записи идемпотентны по источнику и ключу версии. Успешный incremental-сбор в следующий раз перечитывает последние 15 минут перед watermark, чтобы не потерять пограничные обновления. Если один из источников Bitrix недоступен, результат помечается `partial`, а watermark полного успеха не продвигается.

Что эти данные не доказывают:

- `RESPONSIBLE_ID` связывает активность с менеджером, но не доказывает физического автора действия;
- зеркало Max/WhatsApp/Telegram вешается на ответственного карточки, даже если запись в CRM создала интеграция; это наблюдаемая переписка, а не доказательство, кто нажал «отправить»;
- `COMPLETED=Y` не доказывает содержательный контакт с клиентом;
- snapshot-смена стадии показывает разницу между срезами; отдельная REST-история стадий содержит только то, что отдаёт `crm.stagehistory.list`;
- `IS_ONLINE` и `LAST_ACTIVITY_DATE` не являются точным журналом входов и выходов;
- REST не отдаёт переходы по страницам, простые открытия карточек и сохранения формы без изменения данных;
- CRM-событие после просмотра рекомендации показывает только временную связь, но не причинность.

## Команды CLI

Общая справка:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py --help
```

### `snapshot`: основной единый вызов

Для обычной выгрузки используйте `snapshot`: команда сначала выполняет read-only
сбор из Bitrix, затем сразу строит отчёт из обновлённой SQLite. Раздельные команды
`collect` и `report` нужны только для диагностики или повторного построения отчёта
без обращения к Bitrix.

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py snapshot --date 2026-08-20 --format json
```

На VPS JSON можно сразу сохранить на хосте:

```bash
docker exec neuro-rop-api python scripts/manager_trajectory.py snapshot \
  --date 2026-08-20 --format json \
  > trajectory-2026-08-20-v3.json
```
В файл сохранение
```bash
docker exec neuro-rop-api python scripts/manager_trajectory.py report   --from 2026-08-20   --to 2026-08-20   --format json   > /opt/Neuro_rop_practice/runtime/trajectory-2026-08-20-v3.json
```
Без дат `snapshot` использует предыдущий московский день, как и `report`. При
частичном отказе одного из REST-источников JSON всё равно формируется, содержит
`collection_run.status: partial` и список ошибок, а команда завершается кодом `2`.

### `report`: локальный отчёт без Bitrix

Отчёт читает только SQLite и не вызывает Bitrix, транскрибацию или OpenAI.

За выбранный день:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report --from 2026-08-20 --to 2026-08-20
```

Без дат команда строит отчёт за предыдущий московский день:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report
```

Отчёт показывает по каждому менеджеру:

- имя менеджера из текущего deal-control и его ID;
- отдельную хронологию уникальных CRM-действий по каждому номеру сделки и лида;
- исходные тексты активностей и комментариев, историю задач, стадий и значимых полей;
- название воронки, если оно есть в локальном справочнике;
- разбивку звонков, сообщений, писем, задач и наблюдаемых смен стадий;
- по каждой рекомендации — все доступные просмотры (клик по сделке в НейроРОПе или открытие ответа Quick Help) и входы в дожим; создание и показ рекомендации в отчёт не входят;
- для каждого просмотра — действия по этой сделке до просмотра, после него и в первые 60 минут;
- активность по другим сделкам в те же 60 минут;
- предупреждения об ограничениях интерпретации данных.

Новые явные просмотры имеют отдельный `occurrence_id`, поэтому повторное открытие одной рекомендации считается новым просмотром, а сетевой повтор того же события не создаёт дубль. Старые события без `occurrence_id` остаются валидными, но означают только «рекомендация была просмотрена хотя бы один раз».

Версии одной CRM-активности, повторно полученные по `LAST_UPDATED`, в человекочитаемом отчёте сворачиваются по `activity_id`. Полное число сохранённых версий остаётся в сырых trajectory events для аудита.

После обновления с v2 на v3 исторический `collect` нужно выполнить повторно. Расширенная v3-версия активности сохраняется рядом со старой краткой записью и становится актуальной проекцией отчёта; старый факт не перезаписывается.

JSON-формат предназначен для локальной технической проверки и может содержать внутренние идентификаторы. Не публикуйте и не коммитьте его:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report --from 2026-08-20 --to 2026-08-20 --format json
```

### `collect`: read-only дозабор из Bitrix

Без дат команда продолжает incremental-сбор от последнего успешного watermark с перекрытием 15 минут. Если успешного состояния ещё нет, она берёт последние 24 часа:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py collect
```

С начала сегодняшнего дня до фактического момента запуска:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py collect --from 2026-08-20
```

За полностью завершившийся исторический день можно указать обе границы:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py collect --from 2026-08-19 --to 2026-08-19
```

`collect` не скачивает аудио, не делает транскрибацию и не вызывает LLM. Он выполняет только read-only REST-запросы `crm.activity.list`, `crm.deal.list`, `crm.lead.list`, `crm.timeline.comment.list`, `crm.stagehistory.list`, `task.ctasklogitem.list` и `user.get`, после чего пишет нормализованные факты в локальную SQLite.

По умолчанию снимаются только значимые стандартные бизнес-поля. Нужные пользовательские поля можно явно перечислить через запятую в `MANAGER_TRAJECTORY_DEAL_UF_FIELDS` и `MANAGER_TRAJECTORY_LEAD_UF_FIELDS`. Полный набор служебных полей намеренно не копируется.

Для одного или нескольких менеджеров параметр повторяется:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py collect --from 2026-08-20 --manager-id 10 --manager-id 20
```

Watermark сбора общий для manager trajectory, а не отдельный для каждого менеджера. Поэтому `collect --manager-id ...` используйте только для осознанной диагностики: успешный частичный сбор способен продвинуть общий watermark, хотя остальные менеджеры за этот период не были прочитаны. Для штатного дозабора основной базы запускайте `collect` по всем настроенным `manager_ids`, а одного менеджера безопасно выбирайте при построении локального отчёта:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py report --from 2026-08-20 --to 2026-08-20 --manager-id 10
```

Если команда завершилась со статусом `partial`, не считайте период полностью собранным: посмотрите перечисленные недоступные источники и повторите сбор позже. Watermark полного успеха при `partial` сохраняется прежним.

### `candidates`: предварительный список кандидатов

Команда читает Bitrix и переиспользует текущий профиль анализа, но не запускает транскрибацию или LLM:

```powershell
.\venv\Scripts\python.exe .\scripts\manager_trajectory.py candidates --from 2026-08-20 --to 2026-08-20
```

Для `candidates` обязательно указывать обе даты. Это отдельный preview кандидатов, а не manager-trajectory report и не snapshot «Ежедневный контроль».

## Чем отличаются три результата

| Результат | Откуда берётся | Обращается к Bitrix | Может вызвать OpenAI |
| --- | --- | --- | --- |
| `manager_trajectory.py report` | Локальные trajectory events в SQLite | Нет | Нет |
| `manager_trajectory.py snapshot` | Сначала Bitrix, затем обновлённые trajectory events | Да, только чтение | Нет |
| `manager_trajectory.py collect` | CRM-факты выбранных менеджеров | Да, только чтение | Нет |
| «Ежедневный контроль» | Persisted deal-control, анализы, чек-листы и коммуникации | При ручном формировании — да | Сам snapshot — нет |
| Автоматический 30-минутный цикл | Deal-control sync, trajectory collect и change-aware анализ | Да, только чтение | Возможно по решению FULL/MINI/skip |

Кнопка «Сформировать отчёт» в интерфейсе сначала обновляет Bitrix, а затем сохраняет новый snapshot. Простое открытие уже существующего отчёта ничего не скачивает.

## Где лежат данные и код

- SQLite: `reports/rop_assistant/rop_assistant.sqlite`;
- CLI: `scripts/manager_trajectory.py`;
- сбор и построение отчёта: `api/manager_trajectory.py`;
- автоматическое расписание: `api/daytime_cycle.py`;
- неизменяемые отчёты к планёрке: `api/daily_control.py`;
- источник manager scope: `storage/rop_db.py`, таблица настройки deal-control.

Не выводите и не коммитьте `.env`, webhook URL, CRM-данные, содержимое `reports/`, JSON-выгрузки, аудио или транскрипты.
