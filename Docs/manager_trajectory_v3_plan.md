# Manager trajectory v3: план расширения

Статус: реализовано и проверено 2026-08-21.

Цель — получить машинный JSON с максимально полным содержательным журналом работы
выбранных менеджеров из read-only REST Bitrix и отдельно сохранить точную телеметрию
использования НейроРОПа. Браузерные клики, переходы по страницам Bitrix, открытия
карточек Bitrix и сохранения формы без изменения данных в этот контур не входят.

## Неподвижные границы

- Bitrix используется только для чтения.
- Существующие v2-события не переписываются и не обогащаются задним числом.
- CRM-факт, `COMPLETED=Y` и `RESPONSIBLE_ID` не доказывают содержательный контакт
  или физического автора.
- Тексты CRM и транскрипции остаются локальными runtime-данными: не попадают в Git
  и технические логи.
- Вложения сохраняются как метаданные, без бинарного содержимого в JSON.
- Технические поля Bitrix не собираются целиком. Отслеживается согласованный набор
  значимых бизнес-полей и явный allowlist пользовательских полей.

## Контракт v3

### CRM-активность

Сохраняются ID активности и сущности, тип, provider, ответственный, автор, редактор,
направление, статус завершения, времена, тема, описание, коммуникации, метаданные
файлов, результат и доступные метаданные звонка. Все версии остаются append-only,
а отчёт проецирует последнюю версию по `activity_id`.

### Дополнительные REST-факты

- комментарии таймлайна с автором и текстом;
- полная доступная история изменений CRM-задач;
- точная доступная история стадий;
- названия воронок и этапов;
- изменения значимых бизнес-полей между снимками;
- наблюдаемые `IS_ONLINE` и `LAST_ACTIVITY_DATE` как presence snapshots, а не как
  гарантированные login/logout;
- доступные сообщения интегрированных каналов без повторной реализации уже
  существующей нормализации коммуникаций.

### Значимые бизнес-поля

По умолчанию: стадия/статус, ответственный, сумма, валюта, вероятность, дата закрытия,
источник и явно настроенные поля следующего шага, следующего контакта, приоритета,
потребности, бюджета, сроков и ЛПР. Пользовательские `UF_*` включаются только через
явный allowlist.

### НейроРОП

Раздельные события:

- `recommendation_generated` — рекомендация или ответ создан;
- `recommendation_shown` — ответ выведен интерфейсом;
- `recommendation_viewed` — конкретный ответ видим менеджеру;
- `quick_help_opened` — менеджер явно вошёл в раздел Quick Help;
- `manager_communication_completed` — менеджер отметил выполнение коммуникации.

`quick_help_opened` получает отдельный `occurrence_id`. Повтор одного HTTP-запроса
идемпотентен, повторный явный вход сохраняется новым событием. Фоновая предзагрузка
не считается входом.

## Этапы реализации

1. Storage: новые типы событий, snapshot значимых полей, presence и точный
   `quick_help_opened`.
2. REST sources: нормализация расширенной активности, task history, timeline,
   stage history, business fields и presence.
3. Collector: подключение источников с независимыми ошибками и без продвижения
   полного watermark при partial-сборе.
4. Report JSON v3: сырые содержательные факты, проекции по менеджерам и отдельные
   счётчики/хронология Quick Help.
5. Text CLI и runbook: понятный preview без потери полного JSON.
6. Проверка: unit tests, полный Python suite, frontend lint/build, `git diff --check`,
   аудит отсутствия Bitrix write-методов и чувствительных данных в Git.

Все шесть этапов завершены. Полная проверка: 502 Python-теста, frontend lint/build.

## Критерии завершения

- повторный сбор не создаёт дублей одной версии факта;
- частичный отказ дополнительного REST-источника явно виден и не выдаётся за полный
  успешный сбор;
- JSON UTF-8 содержит полные локальные тексты без `Unicode escape`;
- обычный просмотр, вход в Quick Help и просмотр ответа Quick Help не смешиваются;
- старый JSON v2 остаётся читаемым, новые отчёты имеют `schema_version: 3`;
- никакой код не записывает данные в Bitrix.
